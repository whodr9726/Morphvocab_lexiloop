# 背单词系统 · BUG 审查手册

> **用途**：每次新增/修改题型、模式或底层机制后，对照本手册逐条审查。
> 每条 = 【现象 / 根因 / 修复 / 审查要点】。最后一节是「新模式上线自查清单」。
> 出现新 bug 时追加到对应分类，不要另开文件。

---

## 一、判分与流程类

### B01 答错后纠错展示卡住不翻页
- 现象：答错弹出纠错后永远停住，不自动进下一题。
- 根因：chunk 判分分支调用 `scheduleNext()` 但漏设 `session.answered = true`；scheduleNext 回调要求 answered 为真。
- 修复：判分处补 `stopAllAudio(); session.answered = true;`。
- **审查要点**：任何新题型的"提交/判分"入口，必须置 `session.answered = true` 后再 `scheduleNext()`。

### B02 错得多了会被"判对"/跳过（历史回归）
- 现象：一词连错 N 次后不再出现，相当于自动通过。
- 根因：旧版本 requeue 有次数上限（requeued 集合），现行代码已确认无上限。
- 修复：无上限；`requeued` 变量保留但永不使用。
- **审查要点**：`if (!ok)` 回队分支必须无条件插入 redo；grep 确认没有任何 `wrong >= N → 跳过` 逻辑。答对与否只看本次 `built === target`，与历史错误次数无关。

### B03 答错后不回队 / 回队位置错误
- 现象：错词隔了很久才出现（排到队尾），或干脆不出现。
- 根因：回队插入位置曾用"找下一个 mode:'new' 条目"定位；教学卡移除后扫描器直达队尾。
- 修复：统一 `gap = idx + 4 + random(0..2)` 插入，所有模式共用。
- **审查要点**：回队插入不得依赖任何已废弃的队列结构特征。

### B04 会话进行中切换题型不生效
- 现象：点了新题型，当前场次后续题目仍是旧题型（表现为"题型突然变成别的"）。
- 根因：题型芯片只写 `state.settings.quizMode`，队列条目的 mode 在会话开始时已固化。
- 修复：芯片点击时改写本场 `idx+1` 之后所有未答条目的 mode（新学/复习走 modeRow，巩固走 consQRow）。
- **审查要点**：新增"会话内可切换"的设置项时，必须同步改写进行中队列；教学条目（mode==='new'）除外。

### B05 mix 混合题型池不完整
- 现象：混合题型永远不会随机到新加的题型。
- 根因：mix 的随机数组是硬编码列表，新增题型后两处（nextQuestion 与 buildConsolidateQueue）都要补。
- 修复：两处均已维护至当前全部题型。
- **审查要点**：新增题型时 grep `['e2c', 'listen'` 确认两处 mix 池同步更新，并同步 modeRow / consQRow 两个芯片行、CONS_QTYPES。

### B06 键盘数字键绕过题型直接判分
- 现象：在拼写/词块题按 1-4 会触发选择题判分（options 是残留值）。
- 根因：全局 keydown 的数字键分支没有排除拼写类题型。
- 修复：守卫排除 new/spell/spellc/chunk/zhChunk。
- **审查要点**：新增非选择题题型时，必须加入数字键守卫排除列表。

## 二、进度与数据类

### B07 "做对了还反复出现"——AI 计划重置进度
- 现象：explanatory 做对多次仍每天出现；账本值与计划文件写入值完全一致。
- 根因：ai_plan.json 的 setProgress 在计划重放时把词的 iv/due 硬设回旧值（due=过去日期 → 每天都到期）。
- 修复：loadPlan 应用 setProgress 前加防回退门控——词的 due >= TODAY（已推进）一律跳过；数据层清空旧计划 setProgress。
- **审查要点**：任何"批量写词进度"的功能，禁止覆盖 due >= TODAY 的词。

### B08 多标签页旧快照覆盖新进度
- 现象：刚答对的词过一会儿进度被回滚（right/due 变回旧值）。
- 根因：服务端整份账本 last-write-wins；旧标签页保存时用它加载时的旧内存覆盖掉新进度。
- 修复：账本加 `rev` 版本号；推送前先 GET 比对，服务器 rev 更新则采纳服务器、放弃本次推送；visibilitychange 切回标签页时在首页自动采纳最新账本；**服务端强制校验 rev**（POST 的 rev 小于已存 rev → 409 拒绝），旧版本页面（无 rev）无法写入，彻底堵死绕过路径。
- **审查要点**：服务端必须自证写入顺序，不能只靠客户端自觉。
- **审查要点**：任何写服务端的路径不得绕过 rev 比对；新标签页打开页面必须走 adoptServerState。

### B09 进度数据分裂（多浏览器各记各的）
- 现象：Chrome 和内嵌浏览器进度对不上，复习数量越滚越多。
- 根因：localStorage 跟浏览器走；两份存档互不知情。
- 修复：服务端唯一账本 /api/state（state.json），启动采纳、save() 防抖推送；引入 TEST_MODE 沙盒（?test=1：独立存档 wordApp_test、不读写账本、不上传报告）。
- **审查要点**：测试一律走 `?test=1`；真实账本只允许用户页面写入；AI 排查只读文件。

### B10 今日复习数量与每日复习进度联动（历次返工汇总）
- 现象：复习多少个，巩固练习里"今日复习"数量就掉多少。
- 最终方案：巩固练习的"今日复习"池 = **当天首次打开时到期词的快照**（全天不变）；每日复习卡片照常显示剩余到期数（257→0）。两者完全独立。
- **审查要点**：巩固范围/数量的任何统计必须与每日复习的进度互相独立；禁止巩固作答写入 reviewedToday 等复习侧状态。

### B11 巩固轮次轨道范围错配
- 现象：切了巩固"范围"后开始练习，练的还是旧范围的词。
- 根因：每日一轮的 tracks 是首次建轮时的快照，切换范围不重建。
- 修复：track 记录 pool 标记；开始时 `tr.pool !== 当前范围` → 按新范围重建该题型轨道；轨道"空且没练过"的异常态重置后再进。
- **审查要点**：轨道必须记录来源范围；范围切换必须重建。

### B12 场次报告数字与实际不符
- 现象：报告显示的复习次数比实际少。
- 根因：报告只在场次**正常结束**时上传，直接关标签页的场次不上报。
- 修复：认知对齐——报告只是日志，**进度以账本 state.json 为准**；账本每题即存。
- **审查要点**：不要用 reports 校对进度正确性；校对只看 state.json 的 history 与 progress。

## 三、设置与计划类

### B13 设置改完刷新就丢
- 现象：设置里改新学/复习数量，刷新后回到旧值。
- 根因：loadPlan 每次加载都拿 ai_plan.json 覆盖设置。
- 修复（两阶段）：①planSig 签名门控——内容没变不覆盖；②最终方案——**数量字段从计划机制中彻底移除**，计划只含 banner 与 setProgress，每日数量完全归用户设置管（签名门控挡不住"每次更新计划文件都触发一次重放"——只要改过计划文件，用户设置就被踩一次，B13 因此复发过一次）。
- **审查要点**：任何"启动时应用外部配置"的逻辑必须有幂等门控，且配置项里不得包含与用户设置重叠的字段。

### B14 内嵌浏览器测试污染真实数据
- 现象：AI 的自动化测试在用户账本里留下答题记录、改了词的进度。
- 修复：TEST_MODE（`?test=1`）——独立 localStorage 键（wordApp_test）、不读写 /api/state、不上传 /api/report、不应用 AI 计划；页脚显示 v*-test 以便区分。
- **审查要点**：AI 排查/验证一律 `?test=1`；真实账本核对只读 state.json。

## 四、渲染与样式类

### B15 词块竖排占满屏幕、答案要滚动才能看到
- 现象：词块一个占一整行竖排 6 行；纠错弹出在视口外。
- 根因：`.choice-area`（纵向列）在样式表中晚于 `.chunk-area`（横向换行），同特异性后者被覆盖。
- 修复：`.choice-area` 改两列网格；`.choice-area.chunk-area` 双类选择器（特异性更高）强制横向换行；拼接槽移到题目下方。
- **审查要点**：新增答题容器样式时检查与 `.choice-area` 的特异性关系；新界面必须截图目视确认一屏内完整。

### B16 选项/反馈内容缺失
- 现象：听音辨义点"看答案"只显示中文，没有单词和词性；组合拼写没有"不记得"入口。
- 修复：giveupListen 反馈补大字单词+词性+释义；词块类题型统一带"不记得，看答案 😵"（判错回队）。
- **审查要点**：所有题型的纠错/看答案展示统一为【大字英文单词 + 词性 + 中文释义】三件套；听中文题型看答案后额外朗读英文读音（见 B18）。

## 五、音频类

### B17 中文读音 404（历史）
- 根因：生成脚本 rel_path 写 audio/z/ 而目录是 audio/zh/。
- 修复：索引重建。
- **审查要点**：音频索引键与文件路径的目录段必须一致。

### B18 各题型播报内容规则
- 规则：听中文题型（听中文写词/听中文选词/组合拼写/意象组合）题面与重听**播中文**，绝不播英文泄答案；介词规则的中文播**规则全文**而非词表释义；**答错/看答案后朗读英文读音强化记忆**（只读英文）；意象组合报英文。
- 修复中曾发现：组合拼写播词表释义缓存会泄答案 → 介词池跳过缓存直接合成。
- **审查要点**：新题型接入 renderQuestion 尾部音频分支时，明确它属于"听中文组"还是"读英文组"；重听按钮内容与题面一致。

## 六、数据文件类

### B19 源书截断坏释义（objective "adj. [哲" 等 50 个）
- 分类：40 个多词性截断（只剩 "v. &"）、7 个学科标签截断、3 个其他错漏。
- 修复：转换器 tools/build_webapp_words.py 内置 OVERRIDES 人工校对表，重新生成即自动应用。
- **审查要点**：遇到释义可疑先查 lexicon.json 源头；修复写进 OVERRIDES 而非直接改生成物（防重生成丢失）；单字正常释义（n. 竹）与带学科标签的完整释义（n. [医]肝炎）不属于坏数据。

### B23 中文朗读把词性标记读成英文
- 现象：多词性词的中文音频里 "v." "int." "pl." 被读成英文字母，不报词性名。
- 根因：中文音频生成脚本的 clean_zh 未处理释义正文内嵌的词性标记（首词性已转中文，正文内嵌的漏了）。
- 修复：运行时 sanitizeZhText（词性标记→中文词性名）+ zhCacheOk（正文含词性标记的词跳过坏缓存改用合成）；生成脚本 clean_zh 同步修复，重生成后缓存恢复零延迟。
- **复发教训**：首版修复正则要求词性标记前有分隔符，漏掉"紧贴中文字"形态（"光荣v. 尊敬"，共 698 词）；且 Python 与 JS 的  对中文字符行为不同（Python 把中文算 \w， 不成立；JS 不算，成立）——跨语言正则一律用显式 lookbehind `(?<![a-zA-Z0-9])`，不要依赖 。缓存重生成以文本哈希判断，正则修复后必须再跑一轮才能覆盖漏网词。
- **审查要点**：任何把结构化字段拼进朗读文本的场合，先消毒标记符号；缓存音频的生成文本与运行时文本必须同源同规则。
- **复发链（B23-2/B23-3，共三次）**：①首版正则要求词性前有分隔符，漏"紧贴中文"形态（698词）；②改正则时把替换回调参数从 (m,pre,tag) 改为 (m,tag) 只对了一处，另一处回调与新正则的捕获组数量不匹配 → tag=undefined → 词性名静默丢失；③再改时又把 (…) 写成 (?:…) 非捕获组 → 同样静默失效。三次的共同教训：**正则与回调是强耦合对，改其一必查其二；改完必须在页面上用真实函数跑多词性样例（contrary/smoke/even/ought/westward）验收，不能只看代码**。全库扫描脚本（Python 复刻页面逻辑）可快速兜底。
- **形态清单（v5.4 已全部覆盖）**：`v./n./adj./vt./vi./adv./ad./aux./a./pl./sb./sth.`，半角/全角句点，"词性紧贴中文"（光荣v.），"缩"标记，"(pl.)"括注内不切，"=English"行内对译截断。

### B24 看答案/答错后，后续题目全部不自动朗读
- 现象：点"不记得，看答案"后，下一个词（及之后的词）不自动朗读，只能手动点重听。
- 根因（两次定位）：①答错强化朗读与下一题播报竞争；②**真正的卡死源**——stopAllAudio 对播放中的 MP3 调 pause()，而暂停的音频不触发 ended 回调 → ttsBusy 永久卡 true → 之后所有 speak() 被吞（手动重听之所以能恢复，因为 replaySpeak 里的 stopAllAudio 会把忙标志归零）。翻页时长不是原因（已回退 1.7s 实验）。
- 修复：MP3 播放补 `a.onpause = done`（暂停即释放忙标志）+ renderQuestion 渲染新题时 stopAllAudio() 归零兜底。
- **叠加根因（真正的首因）**：gen_tts_audio.py 的 write_index 只在"有新文件生成"的批次循环里被调用——单侧重生成清空了英文索引后，重跑 `--en-only` 因"待生成 0"而从不重建索引 → AUDIO_INDEX 永远为 {} → 答错强化朗读无声。修复：main 尾部无条件 write_index + write_index 单侧跑时并回另一侧旧索引（不清空对方）。
- **审查要点**：单侧维护的数据文件，写入函数必须保留另一侧；"全量已存在→跳过生成"的快路径也要执行索引/清单落盘。
- **审查要点**：媒体元素的 pause 与 ended 是不同事件；用 ended 判定播放完成的必须同时挂 pause/abort/error 回调，否则中断路径会让状态机卡死。
- **审查要点**：任何自动播放入口不得假设音频子系统空闲；新播放周期开始时强制重置播放状态。

### B25 长会话后音频整体静音（间歇性）+ 中英文各两种音色
- 现象：复习几百词后某词（如 indirectly）完全无声，时好时坏；中文有时是浏览器合成音色、英文有时是合成音色，与预生成 MP3 混杂。
- 根因：①Chrome 长会话中 speechSynthesis / Audio.play() 会假死——onend/onpause/onerror 均不触发 → ttsBusy 永久卡 true → 后续全部静音（B24 的另一条触发路径）；②看卡流中文此前固定用浏览器合成（不走 MP3）→ 音色不统一；③zhCacheOk 门控让 698 词退回合成 → 第二种中文音色。
- 修复：**音频看门狗**（1.5s 巡检：忙标志>3s 且实际无任何在播 → 强制复位续播，自愈任何卡死路径）；中文统一优先 MP3（缓存重生成后索引可信，zhCacheOk 退役）；看卡流中文改走 MP3，无缓存才合成兜底。
- **审查要点**：依赖回调判定的资源（音频/合成）必须有超时看门狗，回调丢失是常态不是异常；同一语言的所有播放入口必须汇聚到同一音源选择器（zhAudioFor），禁止各入口私自决定用合成还是缓存。
- **追加（B25-2）：看卡中英文同时朗读**——翻卡时 stopAllAudio 暂停旧音频，其 onpause 回调异步迟到；此时新卡的中文已在播，旧回调错误复位忙标志 → 英文被提前放行 → 中英重叠（重叠的混音听起来"机械"，易误判为音色问题）。修复：**播放令牌**（playToken）——每次开播递增令牌，回调携带令牌，停播/看门狗复位时令牌作废一切在途回调；迟到回调变成空操作。done/done2/400ms 保险三处全部挂令牌。
- **审查要点**：异步回调必须携带世代/令牌校验，"暂停-重启"场景下的迟到回调是重叠类 bug 的标准根因。

### B27 长会话全部静音复发——看门狗被浏览器"自报在播"蒙蔽（v6.4 硬超时根治）
- 现象：复习约 360 词后全部题型静音（听中文/组合拼写/听写等），中英文全无声，F5 刷新才恢复。B25 看门狗上线后仍复发。
- 根因：看门狗判断"是否真在播"依赖浏览器自报状态（`speechSynthesis.speaking/pending`、`lastAudio.paused/ended`）。Chrome 长会话（数百次播放）后引擎假死时会**自报活着**——pending/speaking 卡 true、音频元素停在"播放中"却永不 ended → `playing` 恒真 → 看门狗永不复位 → ttsBusy 卡死 → 所有 speak() 被吞。叠加次级 bug：speakZh 直接置 `ttsBusy=true` 但不更新 `busySince`（看门狗拿陈旧时间戳计龄）。
- 修复：① **45s 硬超时**——不信任自报状态，单条播放超时强制复位 + `speechSynthesis.cancel()` + `lastAudio.pause()` 拆掉卡死源再续播（真实音频最长约 10s，绝不误杀）；② 连续 2 次硬超时 → 弹「🔄 一键恢复声音」提示（点击 location.reload()，进度实时已存放心点）；任何自然完成把计数清零并收起提示；③ speakZh 补 `busySince` 刷新；④ `document.hidden` 时跳过看门狗判断（后台计时器节流防误杀）。
- 验证：?test=1 沙盒 stub 模拟假死（defineProperty pending/speaking=true + Audio.play 永不 resolve）——旧逻辑 6s 时仍忙（蒙蔽复现）；新逻辑 45s 复位、busyHangs 正确计数、二次超时弹提示，10 项断言全过。
- **审查要点**：看门狗不能信任同一引擎的自报状态，必须有与自报无关的墙上时钟硬上限（上限必须 > 最长合法播放时长）；直接置忙标志的入口必须同步刷新看门狗计时基准。

### B28 每日复习上限只管单次队列、不管当日累计（v6.5 额度制+跨天摊开）
- 现象：积压日到期 1068 > 上限 750，用户复习 113 个后重进仍显示满 750（队列用后面的词补满），"每日上限"形同虚设；且超额积压全部堆在当天，越滚越多。
- 根因：dueList(p, cap) 的 cap 只约束单次队列长度；当日已复习量（reviewedToday）不参与扣减；超额到期词没有向后续日期摊开的机制。
- 修复（v6.5）：① **额度制**——revQuota(part) = 每日上限 − reviewedToday.length，buildReviewQueue 与首页计数/按钮全部接额度；额度用完且有积压 → 显示"今日额度已用完 ✓ 剩 X 个明天继续"并置灰按钮。② **跨天摊开**——ensureDay 时 spreadOverdue()：到期词 > 上限 → 按优先级（wrong↓, ease↑, due↑）保留当天额度，其余依次填后续日期，每天填到上限为止（考虑该日已有排期），只往后推绝不往前拉（B07 方向安全）。
- **审查要点**："上限/额度"必须区分"单次队列长度"与"当日累计"两种语义；reviewedToday 只由每日复习写入（B10），巩固/加练不得消耗额度；摊开只修改 due 且方向只能向后。

### B26 设置改动后刷新就回跳（防抖推送 + 服务器优先叠加）
- 现象：设置里关掉开关，刷新后勾又勾上。
- 根因：save() 的服务端推送带 1.2s 防抖；重载时 adoptServerState 以服务器为准。改完立刻刷新 → 新值还在防抖窗口里没上传 → 服务器旧值（rev 相同）反把本地覆盖。
- 修复：**save() 每次递增 rev**——本地刚保存未推送的变更 rev 必然高于服务器，重载时本地必胜并自动补推（推送/采纳路径不再二次递增，保持"一次保存一次递增"的语义）。
- **审查要点**："防抖上传 + 服务端权威"的组合里，权威判定必须能识别"本地有未上传的更新"；版本号要在写入端（save）递增而不是上传端，否则防抖窗口内的退出必丢一次变更。

### B20 事件冒泡双触发（历史）
- 现象：拼写框回车同时触发提交与翻页。
- 修复：spellInput keydown `stopPropagation()`。
- **审查要点**：输入框内键盘事件必须 stopPropagation；全局 keydown 守卫按题型排除。

### B29 精简朗读被"缓存优先"旁路——多义项词全读长串（v6.6 缓存同源把关）
- 现象：精简朗读开关开着，听中文类题型（听中文写词/听中文选词/组合拼写）每次都读"首词性全部义项"的长串，混乱难听。
- 根因：renderQuestion 听中文分支"中文一律优先 MP3 缓存"（B25 音色统一的决定），而缓存 MP3 由 gen 脚本按 **m[0] 全文**录制（不截义项）——zhSpeakText 的精简文本算了、但只在"无缓存"时才用上，开关被缓存旁路。
- 修复（v6.6）：按 B23 同源原则把关——cacheText=sanitize(m[0]) 与 zhText=zhSpeakText(entry) 比较：一致（单词项/双义项词）用缓存；精简开启且不一致（多义项词）改合成读精简；精简关闭维持缓存优先（原行为不变）。代价：多义项词音色为浏览器合成。
- 修复（v6.7，用户发话后）：新增第三套「精简版」缓存 audio/zhc/ + 索引 AUDIO_ZHC（gen 脚本 --zhc-only，Python 复刻 zhSpeakText 全管线，400 词含 150 刁钻形态与页面函数逐字比对一致后才量产）。音源优先级：精简开 → AUDIO_ZHC → 全文缓存（内容一致时）→ 合成；精简关 → AUDIO_ZH。精简文本与全文同哈希的词自动复用 zh 文件不重复生成（9601 条复用 4383 + 生成 5218）。
- **审查要点**：任何"缓存优先"的音源选择，必须校验缓存内容与当前应播文本同源同规则；如果开关只改文本、不改音源选择逻辑，开关必然被缓存架空。

### B32 长场次 200~250 答后全场哑、点喇叭无效、恢复提示永不出现（v6.12 软路径加固+play 挂起看护）
- 现象：单日累计作答 200~250 次后，🔊 重听完全无声、页面再无任何声音，刷新才恢复；v6.4 的「一键恢复声音」toast 从未出现。
- 根因（子代理只读审查定位）：①每次播放 new Audio 不复用不拆源+每题预加载再建多个媒体元素 → 数百元素后 Chrome 媒体管线句柄耗尽，play() 的 Promise 永久 pending 且不报错、paused 卡 true；②此死法下看门狗 3s 软路径（自报"没在播"）每次先触发，但旧版软路径只复位不拆源不计数 → 45s 硬超时（唯一递增 busyHangs 的地方）永远进不去 → toast 永不出现；每次点 🔊 再泄漏一个挂死 Audio。
- 修复（v6.12）：①软路径同样拆源（cancel+pause+置空）+ busyHangs++，连续 2 次弹「一键恢复」；②新增 playGuard(tok,a)——play() 3 秒未真正启动（paused 且 !ended）即作废回调、pause+清 src 拆源、失败计数；自然完成仍清零。两种死法（挂起不启动 / 自报在播）现在 7~9 秒内都能弹出一键恢复。
- 验证：沙盒桩"paused 恒 true + play 永不 resolve"——第 1 次挂起计数 1/拆源/无 toast，第 2 次 toast 弹出；还原后正常路径计数清零无 toast。6 项断言全过。
- **审查要点**：看门狗的多条复位路径必须共享同一失败计数与用户可见出口——任何一条"只复位不计数"的路径都会让恢复提示出现盲区；Promise 永不 settle 的资源（play()）必须有限时竞争，不能只挂 catch。

### B33 听中文选词选项退化为中文释义（v6.14 修复）
- 现象：c2e 题的选项是中文释义（题干即答案的退化题）——听中文选英文词的选项构造器 makeWordOptions 只有定义没有调用点，nextQuestion 一律走了 makeOptions（中文释义选项）。
- 根因：某次重构丢失调用点；用户长期用 chunk/spellc 题型未触发。
- 修复（v6.14）：nextQuestion 按 item.mode==='c2e' 分派 makeWordOptions（英文词选项，介词动词显示"动词 介词"整体）。
- **审查要点**：新增选项构造器必须确认有调用点；题型分派用 mode 条件覆盖所有题型。

### B34 介词动词类目（vp，v6.14 用户设计）
- 学理：不及物动词后接介词短语（状语），"动词+固定介词"是整体（prepositional verb）——abide by / listen to / rely on。
- 用户设计：三分类（及物=槽、纯不及物=自足、介词动词=vp. 类）；vp 的英文呈现（读音/显示/拼写答案）= "动词 介词"整体；判分 normEn 宽松（空格大小写不敏感）但介词必须带（abideby ✓ / abide ✗ / abide at ✗）。
- 数据：146 词条 205 义（vp_01/02 子代理判定），vp_map.js 存 {词: {义项下标: 介词}}；音频：146 个 "word prep" 英文 MP3 + "介词动词"词性名。
- 代码：enForm(entry) 统一英文形式（20 个呈现/判分点位）；zhReadSeq/POS 映射加 vp；组合拼写块含介词。
- **审查要点**：新增词性必须同步**六处**：POS_CN、ZH_POS_CN、zhReadSeq 正则、gen 的 POS_NAME、**gen 的 build_sense_tasks 义项正则**、validator 的 POS_OK——第六处（义项正则）曾在 vp 上线当天漏掉导致 30 个 vp 义项无音频（终审抽查抓到）。

### B30 精简缓存"复用"映射写错路径——单/双义词精简朗读 404 静音（v6.7 当日热修）
- 现象：v6.7 上线后部分词（首报 sulphide）中文完全无声；波及全部"复用"词条（4383 个单/双义词）。
- 根因：gen 脚本去重分支判断 zh 文件存在后，把 **zhc 的 rel** 写进 AUDIO_ZHC（应为 zh 的 rel）→ 索引指向不存在的文件 → Audio 404，onerror 静默跳过（不卡流程，纯无声）。
- 修复：① 一次性脚本改指 audio/zh 同哈希文件（4380 条）；② 脚本改为 `maps['zhc'][key] = rel_zh`；③ 重启生成。
- **审查要点**：复用/别名类映射，索引值必须指向"真实参与播放的文件"；写完索引必须抽查磁盘存在性，不能只看条目数。

### B31 机械取义不等于常用义——精简朗读人工精选表（v6.8）
- 现象：精简朗读按"第一模块+前两义项"机械取义，但词书义项排序不等于常用度。首报 on：读成"形容词，连接上"，常用义"prep. 在…上"排在第三模块根本轮不到。
- 修复（v6.8）：新增 `data/zh_override.js`（window.ZH_READ_OVERRIDE，值=词书释义原文子串，保持同源）。运行时 zhSpeakText 与 gen 脚本 condensed_spoken 都优先读表；首批人工精选 36 个高频词（on/in/at/by/about/over/before/between/but/or/so/if/as/than/can/should/might/shall/make/take/give/use/feel/become/mean/talk/turn/show/hear/sit/meet/stop/offer/open/stay/send）。
- 已知词书缺口：might 词库只有"n. 力量"（常用"可能"义缺失），override 里用了词库外文本补"可能，也许"；98 词带学科方括号标签（[化][医]等）朗读会带出（如 sulphide"n化硫化物"），待用户发话再清除。
- **审查要点**：覆盖模型是"高频优先 + 用户反馈滚动补充"——用户报一个词，查词书原文、选常用义子串、追加进 zh_override.js、重跑 --zhc-only（该词哈希变化自动重新生成）。全量 9388 词逐词人工精选不现实，勿承诺。

### B21 浏览器缓存旧 JS
- 根因：浏览器缓存老版本脚本，用户看到的行为与磁盘代码不符。

- **审查要点**：每次改 app.js/style.css/index.html 后必须递增版本号；让用户先核对页脚版本再排查行为。

### B22 服务端账本写入接口
- 接口：GET /api/state（无账本 404）、POST /api/state（整份覆盖，验 JSON、限 20MB）。
- **审查要点**：账本文件 webapp/data/state.json 是唯一事实源；改服务器代码后需重启进程才生效。
